## 背景与问题

使用者自购第三方中转 API 跑 Codex（OpenAI `gpt-5.x` 系，走 Responses API）。中转链路不透明：
付的是旗舰模型的钱，后端可能是量化版、同族小模型、别家开源模型，或是同一模型被跑在更低的
reasoning 档位上——**且通常不是一开始就换，是跑一阵后悄悄降配**。

现有仓库已经能对**单个**端点做「还是不是原来那个模型」的二元判定，但：

1. 一次判定要 **480 次请求**，横评 5–10 家候选完全不现实；
2. **reasoning 档位那条线完全没有工程化**：`effort` 只在 `/v1/responses` 上生效，而现有代码
   只有两个脚本各自内联 fetch 打它，没有共享的客户端、没有落库、没有与画像层拼在一起；
3. 没有多端点横评、没有持久化、没有界面，每次都是手工跑脚本读终端输出。

本次重构把它从「验证单个已购中转」改造成「**选型时横向评测多家候选，选定后长期监控**」的私有工具。

## 目标用户与成功标准

**用户**：仓库所有者本人，唯一使用者。私有部署，不对外发布、不出售。

**成功标准（里程碑 1 的验收，可观察）**：

> 用这个工具对 ≥3 家候选 Codex 中转跑完一轮横评，读它给出的分维度对比表，
> **据此真的选定一家并完成下单**——而不是「代码跑通了」。

次级标准：
- 一次横评（3 家快筛 + 其中 1 家续跑精确）的**逻辑探针总数** ≤ **400**。逐层实际数：
  **L0a 2（GET）+ L0b 24（`protocol:"chat"` 时 2）+ L1 15 = screen 41／端点**；full 再加 L2 180。
  故 `3 × 41 + 180 = 303`，留余量。
  ⚠️ **这里数的是逻辑探针，不是 HTTP 请求**——有重试时后者更大，两者的区别见「接口契约」；
- **golden test 不会再静默关闭**：上游数据已拉取时 G0-G2 实际运行且通过；数据缺失时
  `npm test` **以非零退出码明确失败**并打印补救命令，而不是 skip。

**里程碑 2 的标准**（不属于本次验收）：网页可从另一台设备经 Cloudflare Access 打开并查看历史结果。

## 关键决策

| # | 决策点 | 选择 | 理由 |
|---|---|---|---|
| 1 | 方法论架构 | **分层混合**：**L0a 零请求画像 → L0b ~25 次能力探测** → L1 15 次快筛 → L2 180 次精确校准 | 三档判定的成本差一个数量级（判「是不是它」个位数次 / 判「是谁」8 次 / 判「掺了多少」~80 次），统一预算是浪费。L0 拆两半是因为读开放接口与响应头确实 0 请求，而参数接受度矩阵要逐个参数试探，不免费 |
| 2 | 交互形态 | 用户自选**快筛档**（L0+L1）或**精确档**（+L2） | 横评时先廉价筛掉大部分，只对决赛选手花钱 |
| 3 | L2 预算 | **180 次**（6 活格 × 15 次 × 2 模型），弃用 480 | 实测：去掉零信号格后噪声地板 0.074、标准差 0.019，判据余量仍 ~3σ；降到 120 次余量掉到 ~2.2σ，86 次仅 ~1.7σ |
| 4 | 格子选择 | 每次运行前从 `reference/` **现算**逐格信号/噪声，自动剔除零信号格 | 实测 `num10-random` 中英两格对 sol-vs-5.4 信号 JSD 恰为 0.000，白烧 480 次里的 120 次。但死格是**逐模型对**的，不能写死 |
| 5 | 偏置校正 | 所有 JSD 统计量减去同分布噪声地板 | 实测记录的 H≈0.17 / S≈0.18 中约 0.056 是有限采样正偏置，真实值约 0.11 / 0.12 |
| 6 | 计费真实性维度 | **不做** | output 侧原理上不可核：reasoning tokens 不可见却按 output 价计费，已有论文报告可虚增最高 1469% 而软件侧发现不了。做一半会给假安全感 |
| 7 | 性能与稳定性维度 | **轻量版**：整体延迟（p50/p95）、**应答率**、错误码分布。🔴 **三者都是「本次跑过的最高层」口径**，不是「全部探针」的合计——应答率的定义见「判定语义」②的补注表；**错误码分布记进结果文件、里程碑 1 不单独出横评列**（列已 11 个），需要时读文件 | 探针请求本来就要发，顺手记录，边际成本为零。⚠️ **不做「首 token 时间」**——它要开流式才拿得到，而流式带来 SSE 解析、超时语义、`usage` 只在末帧到达三项成本，「顺手、零成本」的前提在它身上不成立。16-token 探针的整体延迟本来就由首 token 时间主导，用它足够 |
| 8 | reasoning 降档检测 | juice 探针进 L0（**只信红灯不信绿灯**）；难题正确率法**六档全标定** | juice 是服务端注入、隔 HTTP 可观测，但自我报告 + prompt 全公开 = 一行正则即可伪造。判定仍靠难题正确率 |
| 9 | 正版参照来源 | 继续用自建 cliproxyapi 网关；现有 `reference/` 先不采新的，按需再采 | 用户明牌决策，见「外部平台与合规约束」表 |
| 10 | golden test | **全保**；数据靠一次性 `npm run fetch-data`；**数据缺失时 fail 而非 skip** | 重构期间要改统计代码，安全网默认关着正是最危险的时候。**抽样小缓存方案已评估并否决**：① `detectReasoningPairs` 是全局前置 pass（门槛 `n ≥ 20 && rsn/n ≥ 0.3`，`vendor/pamela/normalize-core.js:120`），抽样必然改变归一化结果，G0 会红；② `split-scores.json` 约 27,225 模型对 × 40 格 ≈ 109 万行（≈65–130MB），压不进仓库；③ `normalizeRuns` 只接受 `<runsDir>/<id>/responses.jsonl` 目录结构，扁平抽样文件进不去。真正要解决的是「安全网静默关着」，不是「500MB 太大」 |
| 11 | 仓库可见性 | 保持 `private`，但补齐 LICENSE 与 vendor 版权声明 | 探针题库不公开 = 中转商无法针对性硬编码，这是相对 hvoy 的真实优势 |
| 12 | 零依赖边界 | `src/`（采集 + 统计，golden test 覆盖的部分）**零运行时依赖**；`ui/` 允许依赖 | 原约束「整个项目零依赖」收窄为「正确性承重部分零依赖」，写进 `CLAUDE.md` |
| 13 | 存储 | `node:sqlite`（Node 内置，实测 v26.3.0 可用） | 符合核心零依赖；单文件、易备份 |
| 14 | 横评输出 | 分维度独立列，**真实性为默认排序键**，不做黑箱加权总分 | 唯一用户，权重应由他当场定；`relay-radar` 那套写死权重（真实性仅 25%）不适用 |
| 15 | 部署 | VPS + Docker + Cloudflare Tunnel + Cloudflare Access | Workers 需重写代码、golden test 在 workerd 跑不了，且**全球 colo 随机出站 IP 会把网络抖动搅进 JSD** |
| 16 | Web 层实现 | `node:http` + 单页静态 HTML + JSON API，无构建步骤 | 单用户工具路由仅十余条；Access 已在前面挡住鉴权。`ui/` 保留引入依赖的权利但当前不用 |
| 17 | 端点配置 | 数据驱动 `config/endpoints.json`，key 走**该端点 `auth_env` 字段指名的环境变量**（不按 id 推导变量名），缺 key 自动 skip。<sub>⚠️ 早期写的是 `<ID>_API_KEY` 这种由 id 推导的约定，与 schema / 阶段 8 / 验收场景 4 用的显式 `auth_env` 是两套机制，**取显式那套**：id 常含连字符、推导规则要再定一层转义，而显式字段零歧义。</sub> | 借鉴 `cuihuan/llm-gateway-bench`（MIT）的数据模型 |
| 18 | 里程碑 1 范围 | **CLI 横评：无持久层、无网页、无部署**。网页 / SQLite / VPS 全部移入里程碑 2 | **这一条是被实施烟雾测试推翻后重定的**：原定「一步到位」，但连续五轮探针显示 HTTP 层的阻断全部来自跨阶段约定（谁重试 / 什么算参数错误 / 落库由谁调用），而那批约定正是「一步到位」造出来的。缩小范围后只有一个调用方、结果写 JSON 文件，约定大部分不再存在。**代价：网页要等；好处：首次实际选型来得更早，而那才是里程碑 1 的验收标准** |
| 19 | **跨模块契约的事实源** | **代码，不是散文**。字段清单、类型签名、枚举取值域、DDL **一律不写进本 plan**；契约代码 + 契约测试是**阶段 1 的第一个交付**，此后所有阶段的验收只引用它、不重述字段清单 | **第二次触发 BLOCKED_STRUCTURAL 后由使用者拍板换的做法**（2026-08-12）。判据是实测：同一组定义表连续三轮（R8/R10/R12）产出阻断，机制每次相同——定义处改了、5–10 个消费点跟不上，每轮修 N 条新造约 N/3 条。第一次重写只把签名降级成「不变量 + 契约测试」，契约仍留在散文里，所以没治住；第二次把事实源指向一个尚不存在的文件，于是「删掉副本」删成了「删掉唯一定义」。**第三次（2026-08-14，按更新后的 groundwork 交付 gate）才走到底**：字段级内容整块移出文档，探针报回的契约层问题进「待消解清单」由实施任务消解。<br>**对照证据**：阶段 5 有可执行的地面真值（阈值能算、能被独立复算到逐位一致），两轮就收敛；散文契约层九轮没收敛。**代价**：文档变薄，部分细节要等代码写出来才定 |

## 方案概述

三层递进，成本逐层放大，只有前一层报警才进入下一层。

```
config/endpoints.json  ──►  [L0a 零请求画像]  0 次推理请求
                              · /api/status 开放接口（New API/One API 框架）
                              · GET {base}/models 清单（base 已含 /v1）
                              · 响应头特征
                                    │
                                    ▼
                            [L0b 能力探测]  ~25 次请求
                              · 参数接受度矩阵 14 项（effort 8 档 + reasoning.mode 2 项
                                + logprobs + seed + n + temperature）
                              · juice 探针（各 effort 档各 1 次 ≈ 8 次，只信红灯）
                              · 注入量截距（2 次）
                                    │
                                    ▼
reference/genuine-*.json ──►  [格子选择器]  0 次请求（纯本地计算）
                              读参照原始样本 → 逐格算 信号JSD / 噪声地板 / SNR
                              → 输出 L1 用的 top-3 格与 L2 用的活格清单及逐格 reps
                                    │
                                    ▼
                              [L1 快筛]  ~15 次请求（3 格 × 5 次，只采待验模型，走 chat.js）
                              S_screen = mean JSD(待验端点, 本地参照)   ← 不减噪声地板
                              → 与离线标定的 T_pass / T_fail 比 → 绿 / 需精确确认
                                    │
                                    ▼
                              [L2 精确]  180 次请求（6 活格 × 15 次 × 2 模型）
                              H = 对照模型 参照↔待测      （纯外壳差异）
                              S = 待验模型 参照↔待测      （待判定）
                              D = 待测端点上 待验↔对照    （真实模型差异的尺度）
                              全部减去噪声地板；bootstrap 出 S/H 的 90% 置信区间
                                    │
                                    ▼
                              [SQLite]  ──►  [横评聚合]  ──►  [Web UI / CLI 表格]
                                             分维度独立列，真实性列默认排序
```

**数据流**：全部出站请求经同一个出站目录（I-4）——指纹层走 `/chat/completions`，
L0b 与 reasoning 层走 `/responses`，L0a 走两个 GET。
**原始响应逐条写进该次运行的结果文件**（`var/runs/<id>__<tier>__<ts>.json`，含失败样本）。
指纹样本再经归一化 → 按格聚合成分布 → 统计层算距离与判定 → 写进同一文件的判定产物；
聚合层读多个结果文件拼成横评表。
🔴 **重跑边界**：结果文件 + 本地 `reference/` 足以让统计层**不重采就重算**——
前提是选格 / 每格 reps / L1 的两个阈值 / 参照版本都已写进 `meta`（见「结果文件约定」）。
**不是「只读结果文件」**：样本本身推不出这四样。
（里程碑 2 才把这些文件导入 SQLite。）

| 入口 | CLI：`node scripts/<name>.js`；服务：`node ui/server.js` |
| 测试 | `node --test`（内置） |

**环境验证命令**（阶段 0 里程碑用）：

```bash
node -v                                                      # 期望 v24 或更高
node -e "require('node:sqlite');console.log('sqlite ok')"    # 期望打印 sqlite ok，且不带任何 flag
```

不要给代码加 flag（部署时 Docker、CLI、测试三处都要带 flag，是三个新的失败点）。

## 接口契约与数据

### 🔴 本节写不变量与验收标准，**不写字段级定义**

**不写**：字段清单、类型签名、枚举取值域、DDL、函数签名。
**写**：对外接口有哪些、失败时的约定形态、数据存哪、以及**跨模块必须成立的不变量**。

字段级契约由**阶段 1 的第一个任务**产出成**契约制品**（代码 + 契约测试），代码是唯一事实源。

<sub>🔴 **理由是实测，不是文风偏好。** 本文档在这一层跑过 15 轮零上下文实施探针未收敛，
交付时 10 条阻断里 6 条是同一个机制——定义处改对了、散落在 5–10 处的消费点跟不上，
同一份文档对同一件事给出两个答案（类型两处答案、枚举取值域不够、DDL 跟不上状态集、
删副本时删掉了唯一定义）。逐条打补丁修不掉它：每轮修 N 条、新造约 N/3 条。
Markdown 没有任何机制保证 N 处同步，代码里一个 `import` 免费保证。
而同一份文档的**决策层在头几轮就稳定了**，此后 15 轮没再被动过——
**两层的收敛性质不同，不该用同一个载体装。**</sub>

### 契约制品清单

| 制品 | 何时产出 | 锁住什么 |
|---|---|---|
| **契约代码**（`src/contracts.js`） | **阶段 1 的第一个任务** | 下面「判定语义」**八条**：样本按种类分派、有效性判据、失败可区分、两个率的分子分母、两个计数、重试归属与配置校验、采集入口的返回形态、Responses 的不留存标志 |
| **契约测试**（`test/contract.test.js`） | 同上；`I-N` 各在其**归属阶段**追加 | 「判定语义」每条一个用例；「不变量清单」每条一个用例 |

契约代码**零依赖、纯函数、不发任何请求**——完全离线、零 API 成本，所以能第一个做。

🔴 **此后所有阶段的验收只引用契约名或调用契约代码，不再重述字段清单。**
判据：一条验收写成「断言含 A / B / C 三个字段」就是一个会漂移的副本；
写成「某条契约测试通过」就不会——**引用没法和被引用的东西不一致**。
<sub>⚠️ 上一版试过「本节拥有最终解释权、别处可以重述但要一致」这种裁决规则，**它失败了**：
加进来的同一轮里 L2 的分母就又被重述错了一次。裁决规则只能事后判谁对，挡不住副本产生。</sub>

### 出站 HTTP 层：只规定不变量，不规定签名

**这段必须留着，否则后人会「好心」把签名补回来，缺陷随之回来。**
本 plan 的 HTTP 层接口规格**连续三轮触发实施烟雾测试的阻断门槛**。三种设计——统一 adapter、
收紧后的统一 adapter、拆成两套独立 adapter——**每一种单独看都成立，每一种都产出阻断**。
根因不在某个设计，在「**在 plan 里把这一层精确到函数签名**」这件事本身：签名一精确就生出一批
跨章节引用（调用方、DDL 主键、重试归属、错误类别、模块边界、旧脚本），
**矛盾长在引用上，不长在签名上**。

模块路径、导出名、参数名**一律由实施者定**——契约测试是他自己写的，import 得到什么他最清楚。
唯一的结构约束是 **I-4**（所有探针出站 HTTP 集中在同一个目录）。
<sub>⚠️ 上一版在这里留过一个「最小例外」，把两个入口的路径与导出名写死，理由是「契约测试必须 import
某个东西」。那个理由在契约测试清单还写在 plan 里时成立；清单移交给实施任务之后它就消失了——
**减法解**：删掉这个机制，比继续给它补边界条件便宜。</sub>

🔴 **每一项有四种取值，`null` 不等于 `false`**（实施时由首次真实运行抓出来的）：
2xx = 支持；**4xx = 不支持**（端点对该参数的明确表态）；**5xx / 网络失败 = `null`（探过了但没测出来）**；
未探 = `not_probed`。把 5xx 记成「不支持」会把端点抖动的一分钟冻成一条永久的能力结论——
实测中一次 503 潮让画像一度报告「该网关不支持 seed / n / temperature」，而它们只是当时没答上来。

**L0b 的参数接受度画像必须是完整的 14 项**（8 个 `effort` 档 + 2 个 `reasoning.mode`
+ `top_logprobs` + `seed` + `n` + `temperature`），**不许缩水成「只记 temperature 接不接受」**——
`logprobs` / `seed` / `n` 的支持与否是「裸 API vs 订阅逆向网关」的关键判据（见实测存档），
漏了它们画像就残了。

#### 🔴 判定语义（决策层——**契约制品必须锁住这八条**）

这些是「**判定对不对**」的问题，不是「数据长什么样」的问题。怎么表达由实施者定，
**语义一条都不许变**；每条在契约测试里都要有一个会失败的用例。

**① 样本按种类分派，四类样本的「什么算有效」根本不是同一个概念。**
指纹样本（L1/L2 的 chat POST）、能力探针（L0b）、reasoning 题（阶段 7）、
可达性探测（L0a 的 GET）各有各的状态集。🔴 **只有指纹样本有判定用的两个率**，
其余三类不进它们的分子分母；向它们索取有效率应当直接报错，而不是返回一个 0。

🔴 **「成功率」这个词在本项目里指过两个不同的量，必须分名，否则横评表会读错一整列**：

| 名字 | 分子 | 分母 | 谁用 |
|---|---|---|---|
| **有效率 `valid_rate`** | 归一化判为有效的样本 | 该侧的**指纹**逻辑样本数 | **守门与判定**（<20% → `not_applicable`） |
| **应答率** | 端点给出了响应的样本（非传输失败） | **同一个分母** | **诊断与展示**：区分「端点坏」与「推理污染」；横评表那一列读的就是它 |

🔴 **两个率都只算指纹样本，分母是同一个。** 非指纹样本（L0b 能力探针、reasoning 题、L0a 的 GET）
**不进这两个率的任何一侧**——它们的健康度由**错误码分布**单独反映。
<sub>⚠️ 混用会造出一个真实的误读：L0b 的 24 个能力探针里「参数被拒」是**正常画像结果**，
把它们算进率里，一个健康端点会显示成很低的应答率，横评表把它读成端点坏了。
早期决策 #7 把「成功率」描述成覆盖全部探针的性能量，与这里冲突——**以本表为准**。</sub>
<sub>⚠️ 用同一套状态机套住全部四类会产生做不出来的要求：L0b 明令「只记录接受/拒绝、不看返回内容」，
它的 `answer_class` 无从谈起；reasoning 用整数 grader，仓库现有归一化器只认识 vendor 的指纹题；
而 `/models` 返回 404 是一条**画像结论**（这个端点不实现 `/models`），不是「传输失败」。</sub>

**② 指纹样本「有效」的判据是归一化层的 `answer_class`，不是「文本非空」。**
拒答话术、解释性长句、答非所问都是非空文本，但进不了指纹——把它们算进 `valid_rate`
会让有效率虚高，而 `valid_rate` 正是「推理污染 / 端点不可用」的唯一守门信号，**虚高就是放行**。
口径必须与 `reference/genuine-*.json` 的 `samples[].answer_class` 一致。
🔴 **归一化管线判为 `post_reasoning` 的样本同样不进有效率分子**（它是「补全里混进了推理残留」，
不是可用答案）。⚠️ **它在两层的可达性不同，不是 bug**：产生它的 `detectReasoningPairs` 是全局前置
pass、门槛 `n ≥ 20 && rsn/n ≥ 0.3`（`vendor/pamela/normalize-core.js:120`），
而 **L1 单层只有 15 个样本，永远触发不了它**；L2 单侧 90 个会。
**L1 见不到这个状态是口径决定的，别据此以为哪一层写漏了。**

**③ 「传输失败」与「补全为空」必须可区分。**
前者是「网络 / 端点坏」，后者是「推理模型把 16 token 预算烧在隐藏推理上」——
正是硬约束里的推理守门要抓的东西。两者都拿不到文本，只有错误对象能区分，
**混成一类会让推理污染被网络抖动稀释掉**。
（相应地，非 2xx 与网络错误都不得静默丢弃，见 I-5 / I-6。）

**④ 两个率的分母是「该侧的逻辑样本数」，不是网络尝试数、也不是成功响应数。**

| 层 | 分母 |
|---|---|
| L1 | **15**（单侧，只采待验模型），算一次 |
| L2 | **subject 90 / control 90**，🔴 **分开算两套率、分开过守门，绝不合并成 180** |

<sub>⚠️ 合并分母会直接毁掉「任一侧有效补全率 < 20% → `not_applicable`」那条规则：
subject 90/90 有效、control 0/90 有效时，合并算出 `90/180 = 50%` 不触发守门，
而 control 侧其实完全没数据、H 与 D 都是垃圾。</sub>
<sub>⚠️ 用成功响应数当分母同理：15 个逻辑样本里只有 2 个拿到响应且都有效时，
按响应数算是 `2/2 = 1.0` → 给绿灯；按逻辑样本数算是 `2/15 = 0.133` → `not_applicable`。
**后者才对**——一个八成请求都失败的端点，没有资格拿到「与正版一致」的结论。
所以守门函数必须**显式收下分母**，不许自己从样本数组长度去推：失败样本可能压根没进数组。</sub>

**⑤ 逻辑探针数与网络尝试数分开记，不许合成一个「实际请求数」。**
有重试时两者必然不等，合成一个就一定有一边是错的。**预算核对看逻辑探针数**（它不因重试而变），
**成本与限流核对看网络尝试数**。注意后者数的是**尝试**不是「到达服务器的请求」——
DNS 失败时根本没有请求发出去，但它照样算一次尝试。

**⑥ 重试写死在两个出站 client 内部，`runner.js` 与各调用方不得再做第二层重试。**
否则两层各 3 次 = 单个探针最多 9 次请求。
🔴 **这个数是「总尝试数」，不是「首次之后再重试几次」**——3 就是最多打 3 次，不是 4 次。
（判据：现状 `quick-check.js:63` 的 `for (let a = 0; a < 3; a++)` 数的就是总尝试；
I-8 的测试也断言「前两次 429、第三次成功 → stub 恰好收到 3 次」。读成「3 次重试」会让
单端点实际请求上限从 180 变成 240，而 180 是合规表里对中转商的承诺。）
🔴 **下界 3**（现状即 3 次总尝试，**不得回退**），🔴 **上界 5**（更高会让单端点预算与封号风险失控）。
**越界或非整数的重试配置 → 在发出任何请求之前抛用法错误**，不许 clamp、不许静默回默认值
（clamp 会让「我配了 10 次」和「实际跑 5 次」不一致，预算核对就再也对不上）。
退避延迟必须可配到毫秒级，否则契约测试跑不动——**这是可测性要求，不是调优选项**。

**⑦ 会发请求的入口，除本层产物外还要交出逐条原始样本与那两个计数。**
结果文件要求逐条落盘（含失败样本），采集入口不吐样本这条就无从兑现。
不发请求的纯判定函数不受此约束。
<sub>⚠️ 上一版让 L1/L2 的采集入口只返回判定结果，于是调用方拿不到样本，而结果文件契约要求逐条落盘。
这类洞由契约测试锁住之后在结构上不再可能。</sub>

**⑧ Responses 请求恒发「不留存」标志，且调用方传入的额外字段覆盖不掉它**
（连同 model / input / 输出预算一起）。默认留存会把现生成的探针题面留在对端，
与「题库不公开」这个相对 hvoy 的核心优势直接冲突。**键冲突时抛用法错误**，不是静默忽略——
那是调用方的使用错误。见 I-9。

#### 哪一层打哪条协议（这是事实约束，不是接口设计，必须遵守）

| 层 | 协议 | 为什么 |
|---|---|---|
| **L1 快筛 / L2 精确** | **`/chat/completions`** | `reference/genuine-*.json` 就是用 `src/probe/adapters/openai.js` 打 chat 采的（见 `openai.js:33-39`）。**换协议 = 换外壳 = 与参照不可比**，而参照是整个判定的地基 |
| **L0b 参数矩阵 / juice** | **`/responses`** | `effort` / `reasoning.mode` 只在 Responses 上生效——CLAUDE.md 已实测「打 chat 传 `reasoning_effort` 两个端点都无反应，那是协议错了，不是不支持」 |
| **reasoning 标定与巡检** | **`/responses`** | 同上；现有 `scripts/quick-check.js:65` 与 `calibrate-probes.js:41` 已在打它 |
| **L0a** | 纯 GET | `${origin}/api/status`、`${baseUrl}/models` |

⚠️ **推论一**：`config/endpoints.json` 的 `protocol` 字段**不控制指纹层**，只声明「推理档探测走哪条协议」。指纹层永远是 chat。
⚠️ **推论二**：端点不提供 `/chat/completions` → L1/L2 对它不适用，横评表标 `fingerprint_unavailable`。

### 判定规则（写死，两层各一套）

**L1 快筛**（只采待验模型，与本地参照比）：

```
S_screen = mean_over_cells( JSD(relay_dist, reference_dist) )     ← 不减噪声地板，见下
判定：
  S_screen ≤ T_pass   → 'consistent'   （绿）
  S_screen ≥ T_fail   → 'suspect'      （红，建议进 L2）
  之间                 → 'inconclusive' （黄，建议进 L2）
```

🔴 **`T_pass` / `T_fail` 必须由数据定，不许写常数。** 阈值来自一个**纯离线、0 次请求**的标定，
在 `src/probe/cells.js` 里随格子选择一起算出：

- 用 `reference/genuine-<subject>.json` 自身做重抽样，模拟「真正版端点采 5 次」
  → 得到**真阳分布**，取 `T_pass = p99`；
- 用 `reference/genuine-<control>.json` 冒充 subject 做同样的重抽样
  → 得到**真掉包分布**，取 `T_fail = p01`；
- 若 `T_pass ≥ T_fail`（两分布重叠）→ **L1 对这一对模型不可用**，返回 `usable:false`，
  调用方直接判 `inconclusive` 并提示改走 L2，**不许硬取中点**。

🔴 **重抽样算法必须逐项写死，不许由实施者自选**（下面五项任改一项，标定值就变）：

| 项 | 取值 | 为什么是它 |
|---|---|---|
| 抽样方式 | **有放回 bootstrap** | 快筛实际是从模型真分布里抽 **5 个新样本**；用 30 条经验分布模拟这件事就是有放回。无放回抽的是参照自身的子集，方差被有限总体修正压小，`T_pass` 偏紧 → 正版端点更容易被误判成黄灯 |
| 重抽次数 | **20000** | 实测：有放回 4000 次时 200 个 seed 里 190 个给同一值（相对极差 8.2%）；**20000 次时 200 个 seed 全部给出完全相同的值**（极差 0）。整个标定耗时 **106ms**，没有省的必要 |
| 随机源 | `mulberry32`，**`seed = 42` 写死**；**每组各一条连续流，跨全部 trial × cell 连续取数**（见下方伪代码） | 标定要可复现。🔴 **「每格各起一条流」是错的**——实测那样 `T_fail` 会变成 `0.3576`（对的是 `0.3412`） |
| 参照侧分布 | **直接用 `refSubject.fingerprint[cell]`**，不从 `samples` 重建 | 两种做法结果不同（`0.0799736861` vs `0.0799824202`）。选已落盘的 `fingerprint` 是因为**线上比对时用的就是它**，标定必须与之同口径 |
| 分位数 | **nearest-rank**（`sorted[ceil(n·p) − 1]`） | 插值法在离散取值上会造出样本里不存在的阈值 |
| 精度 | **判定用原始浮点值，只在 CLI 显示时格式化** | 先舍入再比会让 `S_screen = 0.0795` 这类边界样本翻面 |

```js
// 抽样池 = 该格 answer_class === 'valid' 的 normalized 值；empDist = 整数计数 / 5
const positiveRng = mulberry32(42);   // 两组各一条，各自从 42 起
const impostorRng = mulberry32(42);   // 独立重新起流，不是共用同一条
// 每组内：for (trial of 20000) for (cell of 3) —— 从本组那一条流上连续取数
score = mean_over_cells( jsd(empDist(draw5), refSubject.fingerprint[cell]) )
```

**用仓库现有参照、按上表口径实测的值（2026-08-11，L1 = `num100-random|zh` +
`color-random|en` + `num100-random|en`，每格 5 次）**：

| 情形 | mean | p01 | p99 |
|---|---|---|---|
| 真正版（sol vs sol 参照） | 0.030547 | — | **T_pass = 0.07997368614112692** |
| 真掉包（5.4 冒充 sol） | 0.525946 | **T_fail = 0.34121235356437096** | — |

两分布**完全分离**（间隔 4.27 倍）。上面这四个数**已由两方独立实现分别算出、逐位一致**，
可以直接当回归基准用。这两个阈值是**这一对模型 + 上表口径**的标定结果，
换 subject/control 必须重算——所以它由代码算，不写死在文档里。
<sub>⚠️ 本节此前写的是 `0.066 / 0.35`。那是**无放回**口径下某个 seed 的结果，而无放回在
200 个 seed 上是**双峰的**（0.052 占 141 次、0.066 占 59 次，相对极差 23.9%）——
即「按文档复算得不到文档里的数」。换成有放回后不再有这个问题。</sub>

**L2 精确**（H/S/D，全部已做偏置校正）：

```
S_c ≤ 1.5 × H_c 且 比值 90% CI 上界 < 1.5   → 'consistent'
S_c ≥ 0.7 × D_c                            → 'suspect'
其余                                        → 'inconclusive'（提示加采样或加格子）
任一侧有效补全率 < 20%                       → 'not_applicable'（方法不适用，见硬约束）
```

🔴 **`H_c` 的定义域**：上面两条比值判据只在 `H_c` **显著为正**时有意义。
`H_c ≤ 噪声地板的估计误差`（含为负）时 → **判 `inconclusive`**，不许照公式硬算。
理由：对照模型在两端几乎无差异时（自比、或两端外壳恰好相同），`S_c ≤ 1.5 × H_c` 退化成
`0 ≤ 0` 型比较，bootstrap 出的比值区间宽到无意义——**那不是「一致」的证据，是「这次测不出东西」**。
<sub>（`D_c` 那条不受影响：它是与对照模型的真实差异，自比时同样趋 0，而 `S_c ≥ 0.7 × D_c` 在
两者都趋 0 时不会误报 suspect——但为了避免 0/0，同样要求 `D_c` 显著为正才启用该判据。）</sub>

🔴 **「任一侧」是字面意思：`subject_valid_rate` 与 `control_valid_rate` 分开算，分母各 90**
（见「判定语义」④）。**绝不合并成 180 的单一分母**——subject 满血、control 全废时
合并会算出 50% 而不触发守门，可那时 H 和 D 都是垃圾，`1.5×H` / `0.7×D` 两条判据同时失效。

## 任务分解 · 里程碑 1（CLI 横评：无持久层、无网页、无部署）

> **本里程碑的范围由第五轮实施烟雾测试的结论倒推而来**（决策 #18）：
> 那一轮 16 条不变量里 10 条不可测，而**不可测的全是跨阶段约定**——谁负责重试、
> 什么算参数错误、落库由谁调用、超时怎么注入。这些约定是「里程碑 1 一步到位」造出来的。
> 砍掉持久层 / 网页 / 部署之后：**只有一个调用方、结果写 JSON 文件、不存在存储层协商**，
> 那批约定大部分自然消失。

**里程碑 1 的产物**：一组 CLI + 写在 `var/runs/` 下的 JSON 结果文件 + 终端对比表。
**没有** SQLite、没有 HTTP 服务、没有 Docker/Tunnel/Access。

**结果文件约定**（替代数据库，唯一的存储契约）：
`var/runs/<endpoint-id>__<tier>__<UTC-ISO 秒>.json`，内容 = `{meta, samples[], result}`。
逐条字段由**契约代码**定义（阶段 1 交付），本节只规定必须为真的三件事：

1. `meta` 里 🔴 **两个计数分开记**：逻辑探针数与网络尝试数。**不许再有一个含糊的「实际请求数」字段**
   ——有重试时这两个数必然不等，合成一个就一定有一边是错的。
2. `samples[]` **逐条留痕，含失败样本**（I-5 的留痕要求在这里落地），
   且每条都标明自己是哪一种样本——状态集随种类而变（判定语义①）。
   🔴 **「留痕」包括端点自己回报的元信息**——至少 **model 回显**与 **finish_reason**：
   **缺失时记 `null`，不是省略这个键**。理由不是完备性，是它们各有唯一的消费者：
   **「同一 run 内 model 回显发生跳变」是账号轮换 / 后端切换最值得抓的证据**
   （`CLAUDE.md` 实测存档：relay-A 会轮换，~70% 未注入 / ~30% 注入），
   而 L0 画像的「model 回显」那条信号**没有第二个生产者**；两者也都在 M2 的往返测试清单里。
   <sub>⚠️ 省略键与记 `null` 不是一回事：省略时消费者分不清「端点没报」和「我们没存」，
   那条信号就静默消失了——上一版正是这么丢的。</sub>
3. 🔴 **文件里绝不出现 key**；`meta` 只记环境变量名。

🔴 **重跑边界（这一条是缩过范围的，别读回原来那句）**：结果文件 + 本地 `reference/`
足以让统计层**不重采就重算**——但**必须把「用哪一版参照、选了哪些格、每格几次、
L1 用的两个阈值」一并写进 `meta`**，否则重算的口径与当初不同，算出来的数不可比。
<sub>⚠️ 上一版写的是「任何一层都能只读结果文件重跑」，那句**不成立**：样本本身推不出
选格、reps、阈值与参照版本。要么把它们存进文件，要么把承诺缩到能兑现的范围——
这里选前者加后者：存进 `meta`，并把承诺明确为「结合本地参照可重算」，不是「只读文件」。</sub>

- [ ] 新建 `scripts/compare.js`：遍历 `config/endpoints.json`，缺 key 的标 `skipped(no key)` 跳过；

- [ ] 表格列（固定顺序，**真实性列为默认排序键**，降序=越可信越靠前）：
      `端点` / `真实性判定`（L2 判定优先，无则 L1）/ `S_screen 或 S/H 比值` / `reasoning 档位一致性` /
      `延迟 p50` / `成功率` / `注入量` / `端点类型`（读 l0 结果的 `result.endpoint_kind`）/
      `低置信标志` / `本次逻辑探针数` / `本次网络尝试数`。
      🔴 **这两个计数是「本端点本次横评跑过的各层之和」**：
      `Σ meta.probes` 与 `Σ meta.http_attempts`，遍历本次为该端点产出的全部结果文件
      （`screen` = l0 + l1 两份，`full` = l0 + l1 + l2 三份），由 `compare.js` 求和后写进

      真实性 ← l2 结果文件的 `result.verdict`（无则读 l1 的；**L1 判 `not_applicable`、
      或 L1 遇到协议层错误时**显示 `fingerprint_unavailable`——🔴 **只有这两个来源，
      不许由 l0 画像推断**，见推论二）；
      **成功率 ← 本次跑过的最高层**：`screen` 读 l1 的 `result.success_rate`（单个数）；
      🔴 **`full` 读 l2 的 subject 侧与 control 侧两个成功率**，显示为 `subject / control`。
      **L2 不产出单个合并成功率**（判定语义④：两侧分开算），别去找它——
      合并会把「control 侧全废」这种情况藏起来，而那正是 H 与 D 不可信的信号；
      延迟 p50 ← 同一层结果文件里所有样本 `latency_ms` 的中位数（含失败样本，超时也是真实体验）；
      注入量 ← l0 结果的 `result.injection_tokens`；
      reasoning 档位一致性 ← reasoning 结果文件的 `result.verdict`，
      **`--tier` 的两档都不含 reasoning 巡检，所以该列在没跑过巡检时显示 `not_run`**
      （不是空白，空白会被读成「没问题」）。
      **不输出加权总分。** 提供 `--sort <列名>` 让使用者当场改排序键。
      🔴 **默认排序键是真实性列，而它可能整列不可用**（端点无 chat 面时）：
      排序键只取 verdict 的**四个合法值**（`consistent` / `inconclusive` / `suspect` /
      `not_applicable`），外加两个非 verdict 的行状态，
      次序写死为：
      `consistent > inconclusive > suspect > not_applicable > fingerprint_unavailable > skipped`。
      🔴 两个此前的错：① `low_confidence` **不是 verdict**（它是独立字段、单独成一列展示），
      塞进这个序里实现时无从取值；② 漏了 `not_applicable`——
      而它正是 guards 在有效补全率 <20% 时必然产出的值，也是验收场景 #5 要造的那个。
      **低置信不改变排序位置，只在该行加角标。**
      **验收**：`node scripts/compare.js --tier screen --sort latency_p50` 按延迟排序输出；
      不带 `--sort` 时按真实性列排序。
- [ ] **阶段 8 完成**：对 ≥3 个真实端点跑 `--tier screen`，一次完成，

      `docker run --rm llmfp node -e "require('node:sqlite');console.log('ok')"` 打印 `ok`。
      🔴 **第二条不能省**：`docker build` 不执行应用代码，基础镜像选错（例如 `node:22`）
      要到容器起来才崩，而那时已经在部署现场了。
- [ ] 新建 `deploy/docker-compose.yml`：服务 `app`（`restart: unless-stopped`、
      `env_file: .env`、**`environment: HOST=0.0.0.0`**、挂载 `./var:/app/var`、
      端口映射写死 `"127.0.0.1:8787:8787"`）+ 服务 `cloudflared`
      （`restart: unless-stopped`，token 模式连 Tunnel，指向 `http://app:8787`）。
      🔴 **`HOST=0.0.0.0` 不能省**：容器里的 `127.0.0.1` 是该容器自己的 loopback，
      cloudflared 在另一个容器里，连 `app:8787` 会被拒——M2-C 的部署验收会卡死在这。
      公网隔离靠端口映射的 `127.0.0.1:` 前缀，不靠进程监听地址。
      **验收**：`docker compose config` 无错误；`docker compose up -d` 后
      `docker compose exec cloudflared wget -qO- http://app:8787/api/endpoints` 能拿到 JSON。
- [ ] 新建 `deploy/cloudflared-config.example.yml` 与部署步骤文档（写进 `README.md` 的「部署」节）：
      创建 Tunnel → 指向 `http://app:8787` → 在 Cloudflare Zero Trust 建一个 Access Application，
      策略为「允许指定邮箱」→ 免费额度 50 席位。
      **验收**：文档里的步骤能被一个没参与过本项目的人照着走完，不需要回来问；
      `deploy/cloudflared-config.example.yml` 不含任何真实 token 或域名（用占位符）。
- [ ] VPS 上 `.env` 权限 `600`；`var/` 目录加 cron 备份（`sqlite3 .backup` 每日一次，保留 7 份）。
      **验收**：`ls -l .env` 显示 `-rw-------`；手动跑一次备份脚本产出文件。
- [ ] **M2-C 验收**：从**另一台设备**打开 Tunnel 域名，经 Access 邮箱验证后看到横评表；
      直接访问 VPS 公网 IP:8787 **连接被拒绝**（未开放端口）。

## 测试与验收

**测试策略**：

| 层 | 范围 | 怎么跑 |
|---|---|---|
| golden test（G0-G2） | 归一化逐字段一致、JSD/split-half 复现、AUC/EER 精确复现 | `npm run test:golden`，需 `data/upstream/`（阶段 0 一次性拉取）。**数据缺失时 fail 而非 skip** |
| 契约测试 | 判定语义八条（阶段 1）+ 出站不变量 I-N 逐条一个用例 | `test/contract.test.js`。**判定语义那部分是纯函数断言、0 请求、全离线**；**I-N 那部分用 `node:http` stub 服务器在网络边界断言**（收到的字节、path、请求次数），不对内部函数计数 |
| 单元测试 | 求解器、grader、噪声地板、格子选择与阈值标定、守门规则、bootstrap、juice 解析 | `npm test`，全部离线 |
| 端点集成 | 各 CLI 对真实端点的一次成功执行 | 手动，按各阶段里程碑；**消耗额度，不进 CI** |

**具体验收场景**：

1. **安全网不会静默关闭**：在**已拉取**上游数据的机器上 `npm run test:golden` → `pass 13 / fail 0`。
   把 `data/upstream` 临时改名后同一命令 → **退出码非 0**，输出含 `npm run fetch-data`。
   设 `LLMFP_ALLOW_MISSING_GOLDEN=1` 后 → 退出码 `0`。
   ⚠️ **不要用 `skipped` 计数验这一条**——起点状态下它就是 0（suite 级 skip 不注册内层 test）。
   （`git clone` 后不装任何依赖即可运行——项目无第三方依赖，但 golden test 需要那份一次性数据。）
2. **格子选择器对已有参照**：`selectCells(ref_sol, ref_54, {tier:'l2'})`
   → 恰好 6 格，不含 `num10-random|en` 与 `num10-random|zh`，单模型总 reps = 90。
3. **自比自检**：把 `reference/genuine-gpt-5.6-sol.json` 同时当参照与「待测」喂进 L2
   → `S_c` 落在 `[-0.02, 0.02]`，判定为 `consistent` **或** `inconclusive`。**0 次请求**。
   ⚠️ **不断言必须是 `consistent`**：自比时 `S_c` 与 `H_c` 双双被偏置校正压到 0 附近甚至为负，
   `S_c ≤ 1.5 × H_c` 是 0/0 型比较、bootstrap 出的区间无意义——见「判定规则」里 `H_c` 的定义域那条。
   **这条自检卡的是「统计管线跑通且没有系统性偏移」，不是判定分支。**
4. **缺 key 跳过**：`config/endpoints.json` 里某端点的 `auth_env` 未设
   → `compare.js` 输出该行为 `skipped(no key)`，**整体退出码仍为 `0`**，其余端点正常跑完。
5. **有效补全率守门**：stub 一个只返回空补全的端点
   → L1 判定 `not_applicable`，**不给 `consistent`**，退出码 `0`。
   再 stub 一个 15 次里 13 次网络失败、2 次有效的端点 → `valid_rate = 2/15`、
   同样 `not_applicable`（**分母口径的回归防线**，见判定语义④）。
6. **预算核对**：`screen.js` 逻辑探针 15、`verify-relay.js` 逻辑探针 180
   （两者都在输出末尾**分开打印 `probes` 与 `http_attempts`**；无重试时两者相等，
   有重试时后者更大——**只断言 `probes`，不断言 `http_attempts`**）。
7. **重试不回退**：stub 前两次 429、第三次成功 → 指纹路径与 responses 路径**各自**都能跑完，
   且 stub 各收到 3 次请求；换成恒 400 的 stub → 各只收到 1 次。
8. **密钥不出现在结果文件里**：用形如 `sk-CANARY-<随机>` 的假 key 跑一轮（stub 端点），
   然后 `grep -r 'sk-CANARY' var/ ` **零命中**，stdout/stderr 也零命中。
   <sub>（此前这条挂在里程碑 2 的 db canary 测试上，缩小范围后没人管了——移到这里。）</sub>
9. **重算不重采**：拿阶段 5 产出的一份 L1 结果文件，**只读该文件 + 本地 `reference/`**
   重新算一次判定 → 与文件里记录的判定完全一致，`S_screen` 按 `===` 相等。
   ⚠️ **这条同时卡住 `meta` 必须写全**（用哪一版参照、选了哪些格、每格几次、两个阈值）——
   缺任何一样都复算不出同一个数，它是「重跑边界」那条承诺的唯一验证工序。

## 风险与应对

| 风险 | 信号 | 应对 |
|---|---|---|
| 🔴 **自建网关触发 OpenAI 封号**（上表明文冲突项的失效路径） | 网关日志出现 401/403；ChatGPT 账号收到违规通知 | 立即停用该网关采参照。`reference/` 已落盘的两份不受影响可继续用。若需新参照，改从 OpenAI 官方付费 API 采（需先开通账号） |
| **低比例掺假检不出**（掺假比例 ε ≤ 0.2） | 无——这正是问题所在 | **写进 UI 页脚与 README 的能力声明**。两篇独立论文互相印证这条边界：arXiv:2504.04715 报告 p≤0.2 时 MMD 检验功效塌到显著性水平；arXiv:2607.20860 报告 ε=0.3 时需 m≈80 且代价按 Θ(1/ε) 增长。**不假装能覆盖** |
| **参照过期**（厂商换权重后旧参照不代表正版） | 已知正版端点上 `S_screen` 无故上升；模型版本号变化 | 每季度检查；`reference/*.json` 的 `collected_utc` 在 UI 上随判定一起显示，超过 90 天标黄 |
| **格子选择过拟合单一模型对** | 换 subject/control 后死格判定明显变化 | 格子选择**每次现算**而非写死（决策 #4）；`cells.test.js` 只断言当前这对的结果，换对时重跑 |
| **juice 探针被伪造** | 无法直接观测 | 设计上已处理：**只信红灯不信绿灯**，juice 一致不作为通过依据，输出文案中明写 |
| **中转限流 / 封号导致采样中断** | 429 密集、连续超时 | **重试写死在两个 client 内部**（I-8 与判定语义⑥），次数默认 3、上限 5、越界前置报错；🔴 **`runner.js` 的 `withRetry` 整个删掉**，否则两层各 3 次 = 单探针最多 9 次请求。样本逐条写进结果文件（含失败条目），中断后可据此续采；`compare.js` 单端点失败不影响其余端点 |
| **静默少采导致分布偏移** | `n_valid` 低于预期而无报错 | 每次判定前过 `guards.js` 校验逐格 `n_valid`，**门槛逐层不同**（L1 = 本层请求的 reps=5，L2 = 10；用 10 卡 L1 会让它恒判 inconclusive）；不足的格子排除出均值并在输出中列出；活格不足时判 `inconclusive` |
| **「不设上限慢慢做」导致再次半途停滞** | 超过一个月没有新提交且里程碑 1 未达成 | 缓解而非根治：每个阶段的里程碑都设计为**独立可验证**，且**大部分离线**——阶段 1 与阶段 3 完全离线；阶段 0 需要一次性下载上游数据；阶段 2 除开头抓 fixture 的 **1 次**真实请求外全部离线；🔴 **阶段 4 起的完成条件依赖真实端点**（画像、快筛、校准、巡检都要真的打一次）。别把「离线可验」读成整段不花钱；里程碑 1 的验收锚定在「真的选一次型」而非代码完成度。⚠️ **使用者未设定熄火信号**，这一条只能靠里程碑结构缓解 |
| **Web 服务暴露**（**里程碑 2 才存在**） | 公网可直接访问 8787 | 里程碑 1 无 HTTP 服务，此风险尚不存在。里程碑 2 的既定应对：容器内绑 `0.0.0.0`（cloudflared 是另一个容器，必须如此），**公网隔离靠 compose 端口映射写死 `127.0.0.1:8787:8787`** + 不开防火墙端口，对外只经 Tunnel + Access；验收含「直连公网 IP 被拒」 |
